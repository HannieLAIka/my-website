# Milk · D&D 奇幻传讯与旅途纪事

这是基于 [Milk](https://github.com/aielin17/milk) 原项目建立的独立改造副本。项目希望保留 Milk 原有的聊天体验与字卡传讯机制，同时逐步把界面、功能命名和互动方式改造成 D&D / 奇幻冒险世界中的传讯与旅行工具。

它并不是一个接入 AI、能够实时扮演角色的聊天服务。现有聊天回复仍沿用项目原本的字卡与随机回复机制；新增的旅途事件也由预设内容和本地数据规则生成。

## 项目方向

- **保留原有核心机制**：尽量不改变聊天、字卡随机回复及原有数据存储方式。
- **奇幻世界观改造**：将现代应用式功能逐步转化为奇幻世界中合理存在的物件、记录和工具。
- **旅途体验**：围绕旅伴、旅程、见闻、纪念物与旅行记录，逐步建立一套可持续使用的冒险日志。
- **渐进式开发**：在 Milk 原有 HTML、CSS、JavaScript 架构上分阶段修改，避免不必要的整体重写。

## 当前功能与开发进度

### 旅途纪事匣

原先的多会话管理入口已转向「旅途纪事匣」的设计。它用于整理旅途资料，不代表新增聊天会话，也不应改变现有聊天身份与聊天记录。

目前规划的内容区域包括：

- **旅途篇章**：创建和整理不同的旅程篇章。篇章是记录归档容器，不是聊天会话。
- **旅途见闻**：查看自动发生或主动探索得到的事件记录。
- **珍藏之物**：保存旅途中值得纪念的物品。
- **礼物簿**：整理赠送、收到或计划赠送的礼物。
- **言语摘录**：收藏来自现有字卡内容的角色语句。
- **旅途编年史**：记录重要的时间节点。

其中，旅途篇章与旅途见闻已经进入实际实现阶段；其他区域按项目开发计划逐步完善。各区域的完成状态以当前代码和项目进度记录为准。

### 旅途见闻与事件图鉴

现有旅途见闻系统包含自动事件与主动探索两种产生途径，并将事件保存为旅途记录。已实现的体验包括：

- 每日自动检查并按规则产生见闻。
- 通过「探索未知」主动尝试触发一条见闻。
- 在事件图鉴中管理事件类别和事件模板。
- 将见闻收藏到已有旅途篇章，也可以在收藏时创建新篇章。
- 今日与往日见闻按时间倒序显示。
- 见闻卡片支持较长内容换行，收藏书签保持固定尺寸。

随机事件的数量概率、权重、冷却和日期判断属于需要谨慎保护的既有规则。后续开发应避免在没有明确计划的情况下改动这些机制。

### 关键词组合事件系统（开发规划）

下一步计划在「旅途见闻 → 事件图鉴」中增加关键词素材库与自定义句式模板。

初步设计包括：

- 系统预设与用户自定义关键词。
- 七种关键词分类：地点、来处、人物、行为、发现物、遭遇、活动。
- 用户可以管理关键词，也可以创建自己的事件句式。
- 模板通过占位符调用关键词，例如：`{人物}在{地点}{做了什么}`。
- 不设置额外标签或语义过滤，允许出现意外、荒诞和无厘头的组合。
- 后续再实现关键词抽取、生成预览，并评估如何接入每日自动事件与主动探索。

**注意：关键词组合事件系统目前属于开发规划；在相关代码完成并验证前，不应将其视为已经可用的功能。**

## 技术结构与开发约定

项目沿用 Milk 原有的静态网页技术结构，主要使用：

- HTML
- CSS
- 原生 JavaScript
- localForage / IndexedDB 与 localStorage（按原项目现有实现使用）

项目不以重建框架为目标。新增功能应优先复用现有页面结构、工具函数、存储机制和样式。

### 重要保护原则

修改项目时请遵守以下约定：

1. 不随意改变聊天消息生成、字卡抽取、回复数量概率与延迟等核心行为。
2. 不随意更改现有存储键、会话命名空间或备份格式。
3. 新增数据结构时，应提供安全的数据版本迁移，并保留旧数据。
4. 删除篇章时，不应连带删除归属于该篇章的见闻等记录；应按现有设计解除关联。
5. 新事件应保存必要的内容快照，避免未来修改素材或模板时改变已经发生的历史记录。
6. 读取或保存数据失败时，应保留错误并明确处理，不要用默认数据覆盖可能仍然存在的旧数据。
7. 每次开发尽量限定修改范围，并在完成后列出修改文件、行为变化和验证情况。
8. 静态代码检查不能代替真实浏览器测试；没有运行浏览器测试时，应明确说明。

## 本地运行

这是一个静态网页项目，通常不需要 npm 安装或构建步骤。

可以通过本地静态文件服务器打开项目。直接双击 `index.html` 在部分浏览器环境下可能受到本地文件访问限制；如遇到脚本、资源或本地存储异常，请改用静态服务器访问。

## GitHub Pages 部署

1. 在 GitHub 创建仓库。
2. 将项目文件上传到仓库根目录，确保可以直接看到 `index.html`、`css/` 和 `js/` 等项目文件夹。
3. 打开仓库的 **Settings → Pages**。
4. 将部署来源设置为 **Deploy from a branch**。
5. 选择 `main` 分支和 `/(root)`，保存并等待部署完成。

如果仓库名不是 `用户名.github.io`，GitHub Pages 通常会通过仓库子路径提供网站。部署后应检查页面资源路径、外部依赖、浏览器控制台和本地存储行为。

请注意：GitHub Pages 的公开访问范围取决于仓库与 GitHub 账户的可见性及 Pages 方案设置。若项目包含私人内容或个人记录，请先确认仓库和部署站点的访问权限符合预期。

## 数据与备份提醒

网站数据主要保存在当前浏览器的本地存储中。清理浏览器数据、切换浏览器或设备，可能影响数据的可用性；不同设备之间也不会自动共享本地数据。

进行升级、迁移或恢复测试前：

1. 先使用应用现有备份功能导出备份。
2. 将备份文件保存在网站目录之外的安全位置。
3. 在确认备份可用前，不要对唯一的数据副本进行重置或破坏性测试。

任何涉及存储结构、数据迁移、重置和备份的改动，都应先检查现有实现并谨慎验证。
